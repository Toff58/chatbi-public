# 产品经理视角结论

更新时间：2026-05-19

## 总结

ChatBI 当前已经具备“自然语言提问 -> 安全 SQL -> 数据结果 -> 中文结论/图表”的可用闭环。产品方向成立，下一阶段重点不应是堆更多 Agent，而是把可信度、可解释口径、评测覆盖和客户工作流补齐。

## 产品判断

| 维度 | 结论 |
| --- | --- |
| 核心价值 | 明确。用户可以不写 SQL 获取 App 人群与规模分析。 |
| 当前短板 | 可信度表达不足，用户不知道系统何时做了口径映射、估算或空结果保护。 |
| 架构方向 | 继续单 Agent，强化工具、评测和口径层；暂不拆多 Agent。 |
| 体验方向 | 问数工作台比单表单更适合连续分析。 |
| 商业化风险 | 需要权限、审计、指标口径版本管理和客户数据隔离。 |

## 下一步建议

| 优先级 | 建议 | 目标 |
| --- | --- | --- |
| P0 | 建立 50-100 条标准评测集 | 让每次 prompt/规则/模型改动都有明确通过率。 |
| P0 | 增加口径说明与澄清机制 | 降低“系统自作主张”的感受。 |
| P0 | 形成指标字典/字段字典页面 | 用户能看到可问范围，减少无效问题。 |
| P1 | 增加导出和分享能力 | 更贴近真实 BI 协作流程。 |
| P1 | 增加图表意图识别 | 排行、趋势、占比、分布使用不同图表。 |
| P1 | 做查询缓存 | 降低高频问题成本和等待时间。 |
| P2 | 多用户、权限、审计 | 进入真实客户环境前必须补齐。 |

## 不建议马上做

| 事项 | 原因 |
| --- | --- |
| 多 Agent 拆分 | 当前任务链路窄，拆分会增加延迟和不可控点。 |
| 上向量库 | 规则量还小，本地检索和 few-shot 足够。 |
| 前端暴露 SQL | 客户更关心结论；SQL 应留在日志和开发诊断里。 |
| 自动执行写操作 | 当前产品是问数，不应开放写库能力。 |
